# Security and abuse operations

Status: implementation in this branch; no AWS resources, provider settings, or production deployment were changed. Review the deployment plan before applying it.

## Threat model and enforcement

Anonymous owners are cheap to replace. Signed cookies authorize private history; they are not durable anti-abuse identities. Atomic DynamoDB transactions reserve all applicable per-owner fixed-window counters before provider or storage calls. There are no application-wide quota counters. A new anonymous owner has a separate allowance; overall usage is governed by provider/resource limits, WAF and cost alerts. Rejected transactions consume nothing. Provider failures and disconnected clients still consume a reservation: refunding them would enable cheap retry abuse. There are no automatic provider retries. A fixed window can allow twice its short-window limit near a boundary; daily limits remain separate. The application does not attempt to count active provider streams.

The quota table is separate from shares. It stores operation, owner UUID (for owner counters), window, count, and cleanup timestamp; no content, IP addresses, cookies or provider secrets. Expired counters have a one-day cleanup grace followed by asynchronous DynamoDB TTL deletion. Authorization never depends on TTL deletion. Emergency control records have no TTL. Raw IPs are not accepted from forwarding headers or stored by the application. WAF aggregates on the connection source IP, not a client-supplied forwarded IP. Inspect aggregate traffic first: an AA meeting may share one public IP. Owners can distribute traffic across IPs, so edge limits supplement per-owner quotas.

| Operation                         | Owner allowance                              | Backend outage                      |
| --------------------------------- | -------------------------------------------- | ----------------------------------- |
| Transcription issuance            | 3 / 10 minutes; 15 / UTC day                 | 503, no credential                  |
| Cleanup                           | 5 / 10 minutes; 30 / UTC day                 | 503, no provider call               |
| Share creation                    | 10 / hour; 50 / UTC day                      | 503, no write                       |
| Public reads, including SSR `/s/` | None (session-free; WAF/resource protection) | No quota-backend dependency         |
| Private detail/history            | 120 / minute                                 | fail open; ownership still required |

These are small-launch assumptions (roughly tens of active users), not a forecast of the actual audience. Review them before launch. Each accepted request uses one transaction: two counter updates for paid/write operations, one for private reads; public reads do not access the quota table. Paid issuance also does one strongly consistent control-record read. Successful reservations may overcount actual usage; an outage or ambiguous commit can consume allowance without completing work. Heavy traffic, including rejected requests, can still cost money. WAF and optional database throughput ceilings reduce that risk. Counters are not a per-owner retained-record ceiling. A restrictive lifetime journal limit is deferred; a future atomic counter maintained with share writes would avoid scans and must define retry/idempotency semantics. Nothing deletes established private history.

429 responses have structured `RATE_LIMITED` envelopes and `Retry-After` in seconds for the exhausted window. Transcription/cleanup failures retain original finalized words. Typing and private reading remain available with paid services disabled; saving still depends on storage and its own quota.

## Runtime configuration

Set `QUOTA_TABLE_NAME` to Terraform's `quota_table_name` output and use the existing `DYNAMODB_REGION`/`AWS_REGION` and SSR compute role. `scripts/prepare-runtime-env.ts` copies allowlisted nonsecret quota settings into Amplify SSR runtime configuration. Missing quota configuration fails closed for paid/write operations. Production must use DynamoDB, never the local adapter. The local/default memory persistence mode selects the local quota adapter only outside production; `QUOTA_LOCAL_ONLY=true` exists solely for isolated production-mode browser fixtures, is not copied by the deployment script, and must never be set on a hosted deployment.

`TRANSCRIPTION_DISABLED=true` and `CLEANUP_DISABLED=true` independently disable paid features. Deployment enable flags and the `STT_ENABLED` migration fallback are documented in [Transcription](TRANSCRIPTION.md#runtime-configuration). An explicit canonical enable flag takes precedence over that legacy fallback. For dynamic shutdown use the control records below; environment changes normally require a new deployment. Secrets Manager delivery and provider adapters remain intact. Browser session preparation uses no quota/storage access.

Optional positive-integer overrides follow `QUOTA_<OPERATION>_OWNER_<SECONDS>`, e.g. `QUOTA_TRANSCRIPTION_OWNER_86400=15`, `QUOTA_CLEANUP_OWNER_86400=30`, `QUOTA_CREATE_OWNER_3600=10`, `QUOTA_PRIVATE_OWNER_60=120`. Legacy `QUOTA_*_GLOBAL_*` settings are ignored and are no longer copied into SSR configuration. Only windows present in the typed `config/quotas.ts` policy apply. Invalid known overrides fail deployment/startup validation. Quota backend outages still follow the failure policy above. Separate tables and variables are required for dev/prod. Quota changes do not erase current per-owner counters. Any legacy global counter records are unused and expire through their existing TTL; no private share data is affected.

## AWS deployment

Use the existing backend/bootstrap and role attachment procedure in [the Terraform guide](../infra/terraform/README.md). Do not recreate the existing Amplify application.

1. Set AWS profile/region, select the existing environment-specific backend, and run `terraform init` in `infra/terraform`. Never point dev at production state.
2. Add `amplify_app_id` for the existing application. WAF is optional until explicitly configured, global scope, managed in `us-east-1`. Association uses the Amplify ARN via `aws_wafv2_web_acl_association`, not a customer CloudFront distribution. It covers all branches of that app; use separate Amplify apps for dev/prod. An app can have one ACL: inspect existing associations and import an existing association/ACL into matching resource addresses or coordinate replacement. Do not detach existing protection blindly. AWS may require an eligible Amplify plan and WAF/Amplify integration permissions, including documented `amplify:AssociateWebACL`, `wafv2:AssociateWebACL`, `wafv2:PutPermissionPolicy` and `wafv2:GetPermissionPolicy`, scoped to the selected app/ACL. Grant these to the infrastructure deployer, never the SSR role.
3. Set explicit `budget_emails` and `monthly_budget_usd`, e.g. `{ total = 50, amplify = 20, dynamodb = 10 }` as illustrative small-launch alerts only. Total is account-wide; service budgets are account-wide service filters, not perfect application attribution. Actual 80% and forecast 100% monthly alerts help identify acceleration; forecast requires sufficient billing history. Confirm delivery and any subscription confirmation messages, test recipients, and grant deployment identity Budgets permissions. Alerts can lag and do not stop spending.
4. `terraform fmt -check -recursive`, `terraform validate`, `terraform test`, then `terraform plan -var-file=environments/<environment>.tfvars`. Review the real plan for **no share-table replacement/deletion**, no TTL enablement on shares, correct role/table ARNs, region, state, recipients and Amplify app. Mocked tests cannot establish a safe account-specific plan. Apply only the reviewed plan.
5. Give the selected Amplify SSR branch the existing compute role with the new quota policy. It can update counter keys and read only `control:*`; it cannot write emergency controls. No `Scan`, table deletion, quota-control writes or general AWS administrator permissions are added. IAM authorizes transactional updates through `dynamodb:UpdateItem`, not a fictional TransactWriteItems permission. Control records require a separate operator identity.
6. Set runtime table settings, run preparation, deploy, and smoke-test owner separation, public expiry, one mocked-provider paid request, 429 and backend-failure behavior. Validate application logs redact URL paths at every proxy/hosting layer. Never test limits with real billable loops.
7. WAF starts with `waf_block=false` (COUNT). Observe normal meeting-network traffic, then explicitly enable BLOCK. Five-minute per-IP defaults: paid POSTs 300, share/session POSTs 500, API GETs 5,000, public GETs 3,000. AWS managed CommonRuleSet has no premium rule-group subscription; body-size and body-XSS rules stay COUNT to preserve legitimate reflection text/body limits. Other managed rules can also false-positive: review before enabling. No Bot Control, country blocking or CAPTCHA.

`dynamodb_max_read_units` and `dynamodb_max_write_units` optionally set on-demand table/index ceilings; `-1` retains AWS defaults. Quota and share tables/index use these ceilings. They bound throughput, not monthly dollars, and can throttle legitimate requests; private reads still depend on the share database even though they tolerate quota outages. Tune from measured consumption. On-demand billing and transactional write multipliers still apply.

## Provider controls and exposure

**Soniox manual setup:** use a dedicated project/key per environment. In Organization > Limits set a monthly usage limit and lower email trigger. In Project > Limits set a lower monthly limit/alert and realtime STT concurrent-stream quota appropriate to the audience (start with the default ten, review meeting usage); inspect advanced rate/connection quotas. These settings reject further requests after enforcement, but Soniox explicitly warns that enforcement can lag and excess usage is still billable. Retain an incident-response margin. Restrict the project API key to the minimal supported temporary-key/transcription permissions; do not deploy an organization/admin key to the app. Verify the exact available key scopes in the Console before launch. No Soniox Terraform provider or mutable cost-limit API was invented. The documented Organization API reads usage/limits and manages project keys; use the Console for cost/quota changes.

The Soniox adapter fixes single-use credentials, 60-second establishment expiry and a provider-enforced 600-second stream maximum. It attaches a new random `client_reference_id` per issuance, independent of owner/content, for provider usage correlation. The temporary policy does not pin the browser's model: use the highest permitted realtime model price when estimating exposure. Each issued credential authorizes at most ten minutes. At an illustrative $0.12/hour, a fully used credential costs $0.02. There is no application-wide daily issuance or spending cap; use the provider's project/organization limits and alerts for aggregate usage. Pricing/model permissions, credentials already issued, timing and enforcement delays affect actual spend.

**OpenAI manual setup:** use a dedicated project and restricted key granting only required Realtime client-secret creation and Responses operations. Configure model access, project/model RPM/TPM/audio limits and usage notifications in project Limits; review organization tier limits and billing. Project monthly budgets are soft alert thresholds: requests continue after the budget is exceeded. Provider-enforced rate limits constrain throughput, not monthly dollars. Confirm rate limits for both transcription and cleanup and test them without a billable load test. Keep key permissions separate from dashboard administrator privileges.

OpenAI's adapter requests a 60-second client-secret expiry. It does **not** establish Soniox-equivalent single-use or a server-enforced ten-minute session maximum; browser stop timers are bypassable. No verified hard bound based on ten minutes is claimed for OpenAI. Issuance quotas limit issued secrets, not actual audio minutes or credential reuse. Before enabling OpenAI transcription, validate the current provider transcription-session duration/reuse constraints and model restrictions for this project, set conservative provider limits, and calculate exposure from those verified constraints. Prefer the existing Soniox default for bounded direct transcription. Existing issued credentials/connections can remain useful after application shutdown.

Cleanup has a 10,000-code-point input bound and 8,192 maximum output tokens. Requests are limited per owner; aggregate usage is handled by provider limits and alerts. At the repository's illustrative $0.75/M input and $4.50/M output prices, an intentionally conservative estimate of 40,000 input tokens plus 8,192 output tokens is about $0.067/request with no application-wide daily maximum; tokenization, instruction overhead, pricing and model changes require validation. Typical drafts cost much less. This is an estimate, not a billing guarantee. Set provider RPM/TPM and organization/project limits in addition to application counters.

Sources: [Soniox temporary keys](https://docs.soniox.com/api-reference/auth/create_temporary_api_key), [Soniox limits](https://docs.soniox.com/console/limits), [Soniox realtime quotas](https://docs.soniox.com/stt/rt/limits-and-quotas), [Soniox Organization API](https://docs.soniox.com/console/organization-api), [OpenAI project budgets](https://help.openai.com/en/articles/9186755-managing-your-work-in-the-api-platform-with-projects), [OpenAI Realtime](https://developers.openai.com/api/docs/guides/realtime-transcription).

## Metrics and cost

CloudWatch `AWS/WAFV2` provides AllowedRequests, BlockedRequests, CountedRequests and rule metrics in `us-east-1`. Request samples and full WAF logs are disabled: they can expose bearer paths. The server emits Embedded Metric Format counters in `Doorknob/Security`, `Requests` by fixed `Operation` and `Result` (`allowed`, `limited`, `unavailable`, `provider_error`) in production. They count reservations/denials, not successful provider usage. Use provider usage and AWS billing alerts to monitor aggregate spending; application 429s reflect per-owner limits. The `provider_error` metric includes provider and sanitized server/configuration failures; existing sanitized provider diagnostics categorize them; correlate counts with Soniox/OpenAI aggregate usage and hosting status/429 metrics. EMF publication requires hosting to deliver compute stdout to CloudWatch Logs; verify this after deployment. Configure short log retention and billing alerts in the existing hosting log groups; no full URLs, signed cookies or recovery content should enter them. Do not enable body logging, analytics on share pages or unredacted tracing. Metrics/retention/alarms are not active merely because code exists.

Illustrative incremental AWS cost in a US region: Amplify WAF integration $15/app/month + WAF ACL $5/month + five rules about $5/month + standard WAF requests about $0.60/million = about **$25/month before traffic**, per protected Amplify app. Verify current region/pricing and any WCU/body-inspection surcharges. Managed CommonRuleSet adds no premium managed-group fee. Dev WAF is opt-in to avoid duplicating this baseline. No request logging subscription/storage costs are introduced by WAF defaults.

Quota transactions use two write request units per <=1KiB counter update: four per paid/write reservation and two per private-read reservation; public reads incur no quota-table operations. At illustrative $0.625/million write units and $0.125/million read units, 43,000 paid/write reservations per month cost roughly $0.11 in counter writes plus control reads; 100,000 private reads add roughly $0.125 in counter writes. This excludes share storage/reads, rejected/contended transactions, abuse traffic, log ingestion/EMF custom metrics, regional differences and taxes. Fixed operation/result dimensions bound custom metric cardinality (up to 16 series, roughly $4.80/month at $0.30/series before free tier). DynamoDB quota records are small; TTL deletes in the same region are free. Use actual pricing/traffic, not these examples, for budget decisions.

## Incident response

1. Using an operator role, put `{ "id": "control:transcription", "disabled": true }` in the quota table. In the Console use DynamoDB's item editor, or `aws dynamodb put-item --table-name <quota-table> --item '{"id":{"S":"control:transcription"},"disabled":{"BOOL":true}}'`. New issuance checks this strongly consistently without a cache.
2. Independently put the same disabled record with `id=control:cleanup`. Do not delete counters to restore service. In-flight requests that passed the check may still finish; provider controls/key revocation are necessary for immediate containment of existing streams/credentials.
3. Review aggregate WAF metrics, switch scoped rules to BLOCK or lower thresholds via reviewed Terraform. Do not edit managed infrastructure only in the Console and leave drift.
4. Reduce provider quotas/limits; revoke compromised project keys if needed. Application shutdown does not revoke already issued credentials. Set alert thresholds below the tolerable bill.
5. Inspect only aggregate status, quota counts and provider usage. Do not inspect saved recovery content or copy bearer links into tickets/logs.
6. Restore a feature by setting its control record's `disabled` to false after resolving the cause. Keep provider limits conservative, restore normal WAF thresholds through Terraform, monitor error rates and expand gradually. Reading and manual typing remain possible throughout; an exhausted share quota can still prevent saves until its window resets.

## Privacy and retention

Saved shares contain original text, reading snapshot, creation timestamp, UUID and owner ID. Private history has no automatic expiry; share TTL stays disabled. Public UUID links expire exactly seven days after server-stored creation time, independently of retention. An expired link does not mean the record was deleted. No raw audio is persisted by this app. Unsaved drafts are React memory; transcription/cleanup providers process audio/text under their own policies (`store:false` for cleanup does not mean zero provider retention).

The signed HttpOnly cookie has a 30-day absolute lifetime, SameSite=Lax and Secure in production. Expiry/loss, signature-key rotation or a new browser loses private access; a fresh owner never inherits history. Records are retained even when access is lost. There is no current deletion, per-link revocation or recovery endpoint; recipients may keep copies. A deletion feature is a separate product decision: the smallest option is owner-authorized deletion by record ID, removing the persistent record and disabling its public link, with clear lost-cookie limitations and concurrent-read semantics. Do not enable TTL on private history as an incidental security change.

## Dependency checks

Existing weekly Dependabot updates cover npm and GitHub Actions; CodeQL covers application static analysis. Neither is a substitute for a current dependency advisory check. CI now runs `npm audit --audit-level=high` across runtime and development dependencies. The implementation audit found zero production vulnerabilities, but ten moderate findings in development tooling (`fast-uri` and the minimatch/ESLint/TypeScript-ESLint chain). These remain visible and are **deferred** to compatible tooling updates; the suggested forced ESLint downgrade is outside this hardening change. No high/critical advisories were reported. Do not use `audit fix --force` without reviewing its toolchain changes. Recheck these advisories before release; audit results are time-specific.
