# Application API

This is the HTTP contract for the Next.js BFF in `jft-app`. It supports the current browser's private shares and UUID-link sharing. There are no login endpoints or client-selected owners. See [architecture](ARCHITECTURE.md) for implementation boundaries and [the README](../README.md#getting-started) for server setup.

## OpenAPI contract and libraries

`GET /api/openapi.json` serves OpenAPI 3.1, generated by `@hono/zod-openapi` from the route definitions and the Zod schemas used to validate requests. It is public schema metadata, contains no live shares/credentials, and does not issue a session cookie. HEAD returns its headers without a body; OPTIONS advertises GET, HEAD, OPTIONS.

Each operation owns its contract, selected middleware, and typed handler: [create](../src/shares/server/http/operations/create-share.ts), [list](../src/shares/server/http/operations/list-shares.ts), and [read](../src/shares/server/http/operations/read-share.ts). [Resource method handling](../src/shares/server/http/resource-methods.ts) owns HEAD documentation, OPTIONS, and 405 responses. [Shared OpenAPI helpers](../src/server/http/openapi.ts) provide common schemas/headers and API metadata. [The server app](../src/server/app.ts) registers these operations, configures shared failure handling, applies cache policy, and exposes the specification. Existing Next.js Route Handler files dispatch Web Requests to this app; there is no separate backend service. TypeScript definitions are the sole source of truth. Generated YAML is temporary and is not committed.

To generate and lint the contract locally:

```bash
npm run openapi:lint
```

This writes ignored `.tmp/openapi.yaml` and runs Spectral using [`.spectral.yaml`](../.spectral.yaml). `npm run openapi:generate` generates the file alone. Generation needs no running server, session secret, or network access. The standard `spectral:oas` rules apply; warnings and errors fail. `npm run check` includes this validation, and the GitHub Actions Verify job uploads the YAML as the `openapi` artifact, retained for seven days. There is no committed-YAML drift check.

Spectral checks contract conventions; it complements runtime validation and response tests.

`npm test` uses Swagger Parser to validate the serialized specification and Ajv's JSON Schema 2020-12 validator to check actual response bodies and required headers against it. Shared Zod validation remains authoritative for input transformations/refinements, including rejecting whitespace-only text after trimming. HTTP integration tests also exercise the real Next.js exports and framework boundary.

```bash
curl --silent --show-error --fail-with-body http://localhost:3000/api/openapi.json
```

No generated client or interactive documentation UI is required to consume the document.

## Prepare a session

`POST /api/session` requires an exact same-origin Origin and returns `200 { "ready": true }`. It verifies or creates the existing signed anonymous cookie, without returning an owner ID, renewing a valid cookie, reading history or contacting providers. Foreign/missing Origin returns 403 without setting a cookie. Configuration/signing failure returns the generic 500 envelope. OPTIONS advertises POST, OPTIONS; other methods return 405. Every response is private/no-store.

The browser serializes preparation and explicit retries before recording/saving. It loads history only when Past shares is opened; a history failure does not unset session readiness. Existing share endpoints retain their implicit session establishment for API compatibility. Public readings and bearer-link reads remain session-free.

## Session and response conventions

The server reads the `doorknob-session` cookie. If it is absent, malformed, expired, or incorrectly signed, a private create/list/detail endpoint creates a fresh random anonymous owner and issues a signed cookie with its response. The previous owner is never trusted or restored from invalid credentials; the new history is empty. There is no account recovery UI or endpoint, including when DynamoDB is selected. Cookie-based clients must retain and resend the cookie. Browser code uses same-origin credentials; nonbrowser clients need a cookie jar.

The cookie is HttpOnly, host-only, SameSite=Lax, and scoped to `/`. It has an absolute 30-day lifetime, with Secure added in production. Successful reads do not refresh its expiry. When the browser drops an expired cookie, its next request starts a new owner; an expired credential explicitly sent by a client also starts a new owner. Tabs sharing site cookies share an owner. Isolation requires separate cookie jars, such as a normal profile and a private profile; multiple private windows may share cookies with one another.

Signing prevents tampering; it does not encrypt the payload. The cookie contains the owner UUID and expiry and must be treated as a bearer credential. Do not log it, commit a cookie jar, or put it in an API body or URL. The `ownerId` field is omitted from share JSON; the UUID in the signed cookie is not a secret identifier on its own.

Responses carry `Cache-Control: private, no-store`. Share/error bodies use JSON; HEAD and OPTIONS have no body. Responses are returned directly as a share or an array; there is no `data` wrapper. Errors have this shape:

```json
{
  "error": {
    "code": "SHARE_NOT_FOUND",
    "message": "Share not found."
  }
}
```

Messages are intended for display. Branch on `error.code` and the HTTP status, never by matching message text. The fetch client exposes these as `ApiRequestError.code`, `.status`, and `.message` and does not retry writes. Non-JSON HTTP failures retain their status with a safe fallback message.

## Save-time sharing URL

Create/list/detail responses include `shareUrl`, a relative URL such as `/s/{id}`. It is generated once when the record is constructed, before storage. Resolve it against the application origin for native sharing or copying. Reads return the original URL without renewal. There is no separate link-generation endpoint or extra sharing request. Treat URLs as bearer credentials and never log them.

The public service rejects links seven days after the stored `createdAt` timestamp. Private history/details do not expire. Client query parameters cannot extend link lifetime. Public responses exclude `shareUrl` and owner metadata.

## Read today’s daily text

`GET /api/readings/today?timeZone=America%2FChicago` is public and never creates a session cookie. `timeZone` defaults to America/Chicago and must be a valid Intl timezone. Success is 200 `{ "date": "YYYY-MM-DD", "reading": { "id": "...", "date": "...", "title": "...", "quote": "...", "source": "...", "body": "..." }, "sample": false }`. A date without published content returns `reading: null`. Invalid timezone queries return 400 `INVALID_READING_QUERY`; storage/configuration failures return sanitized 503 `READING_UNAVAILABLE`. GET/HEAD/OPTIONS are supported; other methods return coded 405. Responses are private/no-store at HTTP level; the service maintains its own bounded catalog cache.

The `sample` flag reflects the configured `READINGS_SAMPLE` label for fictional content. The catalog uses annual `MM-DD` keys; response and snapshot dates remain full ISO dates for the selected year. New catalog readings include `quote` and `source`; saved snapshots created before this change may omit both. It never supplies fallback content for missing dates or source failures. See [daily readings](READINGS.md) for timezone preferences and cache behavior.

## Read a public share

`GET /api/public/shares/{id}` requires the cryptographically random UUIDv4, **no session**. The UUID itself is the bearer credential; every saved share can be read by someone who knows its ID during its lifetime. Existing cookies are ignored, including invalid ones; this endpoint never issues or replaces them. The server validates the UUID before storage lookup, then checks the stored creation time before returning content. No client-provided timestamp controls lifetime. Malformed UUIDs, expired shares and nonexistent records return **404/SHARE_NOT_FOUND**. Repository failures return generic 500. No signature or separate sharing secret is used.

Success is **200** with only `{ "reflection": { "id": "...", "date": "2025-04-23", "title": "...", "quote": "...", "source": "...", "body": "..." }, "text": "A fictional thought." }`. It excludes owner ID, share creation metadata, kind and private history. Responses, including failures, carry `Cache-Control: private, no-store`, `X-Robots-Tag: noindex, nofollow` and `Referrer-Policy: no-referrer`. HEAD performs the same UUID and lifetime checks with no body. OPTIONS advertises `GET, HEAD, OPTIONS`; other methods return coded 405 with Allow. No CORS permission is granted.

The recipient HTML page is `/s/{id}` with the same UUID and service boundary. Valid links show the original reading date/title/body and written thoughts. Unavailable links show a generic message (HTML 200); unexpected server failures use a separate retryable error boundary with sanitized diagnostics and an initial HTTP 500 response; this is a minimal reading page, not private-history navigation. Pages have dynamic private/no-store caching and noindex/no-referrer headers and metadata. No session is established. No content-specific metadata or external tracking is added.

These are bearer links: recipients may forward, copy, or save content. There is no immediate revocation, token storage, link version counter, revoke endpoint, or delete endpoint. Future deletion of a share will invalidate its links by removing the record. Expiration denies public reads only and does not delete records. Neither can recall received copies. A process restart loses memory-mode records, while DynamoDB records survive restarts. [Architecture](ARCHITECTURE.md#storage-and-public-sharing-boundary) describes the trust boundary and tradeoffs.

## Create a share

`POST /api/shares`

Optional `readingDate` is an ISO calendar date and `readingId` is the displayed revision ID. The server resolves the date, never client-provided reading text. If omitted, it selects today using the timezone preference cookie, falling back to Central Time. A missing source returns 503 `READING_UNAVAILABLE`; a supplied revision that no longer matches returns 409 `READING_CHANGED` without writing a share. The UI retains the pinned draft, refreshes the current reading, and requires explicit review of that reading followed by another save. The reading snapshot in a successful share never follows later editorial edits.

Send `Content-Type: application/json` and a JSON object containing only `text`:

```json
{
  "text": "A fictional thought.\nOne small step."
}
```

The server accepts at most **10,000 Unicode code points in the raw text**, then trims surrounding whitespace and rejects an empty/whitespace-only result, nonstrings, missing text, and extra fields. Code points match JSON Schema's length semantics; combining sequences may contain several code points. The complete raw JSON body is limited to **64 KiB (65,536 bytes)**, including escaping and whitespace. Hono's body-limit middleware counts actual streamed bytes; a smaller claimed Content-Length cannot bypass this limit. A text-length violation returns 400/INVALID_SHARE; an oversized request returns 413/PAYLOAD_TOO_LARGE before JSON/schema validation. `ownerId`, `id`, `createdAt`, `kind`, and `reflection` are not accepted input fields. The session establishes ownership; the server supplies UUID, UTC ISO creation timestamp, `kind: 'text'`, and the selected reading snapshot. Snapshotting happens when the server saves, so changing the reading later does not alter existing records.

Success is **201 Created** with a share and a relative `Location: /api/shares/{id}` header. This identifies the private resource; the URL grants no access without the correct session. The following example uses fictional text and the local sample reading; the ID and timestamp are illustrative:

```json
{
  "id": "95eff0e1-bca7-4fd1-83d2-42ba330aab22",
  "createdAt": "2026-10-18T12:00:00.000Z",
  "kind": "text",
  "shareUrl": "/s/95eff0e1-bca7-4fd1-83d2-42ba330aab22",
  "text": "A fictional thought.\nOne small step.",
  "reflection": {
    "id": "acceptance-2025-04-23",
    "date": "2025-04-23",
    "title": "Acceptance is the answer to all my problems today.",
    "body": "Today, I can practice meeting life as it is. Acceptance gives me room to pause, let go of what I cannot change, and take one small step toward what I can."
  }
}
```

`reflection.date` is a calendar date, distinct from the creation timestamp. [Shared Zod schemas](../src/shares/model.ts) define the runtime field contract. The [server repository](../src/shares/server/storage/repository.ts) additionally stores `ownerId`; the handlers project records to the owner-visible schema before responding.

## List private shares

`GET /api/shares`

Success is **200 OK** with an array of this session's shares, newest creation timestamp first. No shares is `[]`, not an error. The Map implementation orders equal timestamps by newest insertion first; DynamoDB does not promise tie order. Its owner index is eventually consistent, so a new share may appear in history after a short delay. History is paginated: `limit` defaults to 20 and accepts integers from 1 to 50. When another page may exist, the response includes an opaque `X-Next-Cursor` header; send it as the `cursor` query parameter on the next request, for example `GET /api/shares?limit=20&cursor=<encoded-position>`. The JSON body remains an array. Absence of the header means there are no more pages. A database size boundary can return fewer than `limit` shares. Invalid/oversized cursors and out-of-range limits return 400 `INVALID_HISTORY_QUERY`.

Cursors contain private share positions and must not be logged. They never authorize access: the query owner always comes from the verified cookie. A forged or foreign cursor cannot select a different owner. History is not a snapshot across concurrent writes or index propagation; refresh starts from the newest page and clients should deduplicate IDs across pages. A failed continuation request is an error, not a successful partial page; keep previously displayed shares and offer retry.

## Read one private share

`GET /api/shares/:id`

Success is **200 OK** with the same share shape as creation. This private endpoint requires the owner session. The same UUID also grants public read access through `/s/{id}` for seven days, so it must be treated as a credential. IDs with no corresponding record (including non-UUID strings), and IDs belonging to a different owner all return **404 Not Found** with the same error message. An invalid cookie starts a fresh owner, which cannot read a previous owner's share and therefore receives 404.

## Status and stable error codes

| Status | Code                   | Meaning                                                                               |
| ------ | ---------------------- | ------------------------------------------------------------------------------------- |
| 200    | —                      | List/detail succeeded; only a loaded empty array means empty history                  |
| 201    | —                      | Confirmed creation; clear the saved draft and show confirmation                       |
| 400    | INVALID_JSON           | The JSON body cannot be parsed                                                        |
| 400    | INVALID_SHARE          | Text is missing, blank, too long, or extra fields were supplied                       |
| 400    | INVALID_HISTORY_QUERY  | History cursor is malformed or limit is outside 1–50                                  |
| 403    | CROSS_ORIGIN_REQUEST   | POST supplied a foreign Origin                                                        |
| 404    | SHARE_NOT_FOUND        | Detail record is absent or inaccessible to this owner                                 |
| 405    | METHOD_NOT_ALLOWED     | This resource does not implement that App Router HTTP method; includes Allow          |
| 413    | PAYLOAD_TOO_LARGE      | Raw request body exceeds 65,536 bytes                                                 |
| 415    | UNSUPPORTED_MEDIA_TYPE | POST content type is missing, invalid, or not application/json                        |
| 500    | INTERNAL_ERROR         | Configuration, repository, or other internal operation failed; details remain private |

On failed saves, retain the draft. Correct 400/413 input, use JSON for 415, and check the same-origin/proxy setup for 403. Private reads with invalid cookies start a fresh owner, not account recovery. 500 is generic: resolve the server/connection problem and consider the ambiguous-write caveat below before retrying.

500 can occur on private share operations; OPTIONS and the specification do not require a session. Media types are parsed with the `content-type` library: valid case-insensitive spellings such as `Application/JSON; Charset="UTF-8"` are accepted; syntactically invalid headers and other JSON subtypes are not accepted. A valid header is normalized before the OpenAPI JSON validator runs. POST also compares a supplied Origin to the browser-facing Host and request protocol. A missing Origin is allowed for nonbrowser clients. There is no cross-origin API/CORS support. Deploy behind HTTPS and a proxy that preserves or correctly supplies the original Host and protocol; do not rewrite these to an unrelated internal hostname.

A new session cookie can accompany a controlled POST validation error because the middleware establishes a session first. Foreign-origin rejections and internal 500 failures do not issue a cookie. [Session middleware](../src/server/http/middleware.ts) and [HTTP errors](../src/server/http/errors.ts) own this behavior. POST origin validation runs first: a foreign Origin receives 403 without reading, creating, or replacing a session, even if a supplied cookie is invalid. For accepted origins, verified or fresh anonymous ownership is established before media-type, size, JSON, and schema checks. Invalid cookies never supply ownership.

## HEAD, OPTIONS, and unsupported methods

| Resource          | Allow                    |
| ----------------- | ------------------------ |
| /api/shares       | GET, HEAD, POST, OPTIONS |
| /api/shares/{id}  | GET, HEAD, OPTIONS       |
| /api/openapi.json | GET, HEAD, OPTIONS       |

Hono implements HEAD by running the GET checks and removing the body. A private detail can therefore return 200 or 404 with an empty body and the corresponding GET headers (or generic 500 on server failure). Initial HEAD requests may issue a cookie, just like GET.

OPTIONS returns 204, no body, and the Allow header. It does not read/create sessions, even if a supplied cookie is invalid, and it grants no CORS permission. App Router methods not implemented by a resource (PUT/PATCH/DELETE, plus POST on a detail/spec resource) return the coded 405 envelope, private/no-store, and Allow without issuing a cookie. Methods Next.js rejects before dispatch, malformed transport requests, and framework redirects remain outside the custom JSON envelope.

## Try it locally

Start `npm run dev` in one terminal. In another terminal, run the following with fictional text only. This uses the existing Node.js runtime to extract the generated ID; no additional API tool is required beyond curl.

```bash
doorknob_base_url=http://localhost:3000
doorknob_cookie_jar="$(mktemp)"

doorknob_created_share="$(curl --silent --show-error --fail-with-body \
  --cookie "$doorknob_cookie_jar" --cookie-jar "$doorknob_cookie_jar" \
  --header 'Content-Type: application/json' \
  --data '{"text":"A fictional thought. One small step."}' \
  "$doorknob_base_url/api/shares")"
printf '%s\n' "$doorknob_created_share"

doorknob_share_id="$(printf '%s' "$doorknob_created_share" | \
  node -e 'let body = ""; for await (const chunk of process.stdin) body += chunk; console.log(JSON.parse(body).id)')"

curl --silent --show-error --fail-with-body \
  --cookie "$doorknob_cookie_jar" "$doorknob_base_url/api/shares"
curl --silent --show-error --fail-with-body \
  --cookie "$doorknob_cookie_jar" "$doorknob_base_url/api/shares/$doorknob_share_id"

# A separate client without this cookie cannot access the first owner's share: 404.
curl --silent --show-error --output /dev/null --write-out '%{http_code}\n' \
  "$doorknob_base_url/api/shares/$doorknob_share_id"

# Delete the temporary bearer credential when finished.
rm -- "$doorknob_cookie_jar"
```

The first POST issues the cookie; subsequent requests use it. On a browserless HTTP production-mode run, curl will not send a Secure cookie over arbitrary plain HTTP hosts. Use the development server for this example, or HTTPS for a hosted server.

## Retention and failed-write semantics

Memory-mode records exist only in the same Node process and are lost on restart; replicas do not share that Map. Explicitly configured DynamoDB storage survives restarts and is shared across instances. Public links expire independently of private history. Neither store automatically deletes records. Cookie removal, cookie expiry, and signing-key changes lose private access without deleting records or revoking public links. No manual delete endpoint is added. See [data lifecycle](DATA_GLOSSARY.md#app-data-lifecycle).

An interrupted response can leave a committed share. The browser retains an owner-scoped submission key for explicit retries of the unchanged draft; see [retrying saves](#retrying-saves). Calls without a key can still create duplicates. No automatic retries are performed, and a rejected fetch is not proof that no write occurred.

## Live transcription credentials

`POST /api/transcription/session` issues a temporary credential for the startup-selected speech provider; it does not save text or accept audio. It requires an exact same-origin Origin, an existing valid signed anonymous cookie, and sufficient owner quota. Speech is available by default unless an emergency shutdown control applies. An invalid/missing session is rejected rather than replaced. `X-STT-Provider` asserts the browser's runtime bootstrap, not a user choice. Provider-specific settings and lifecycle are documented in [Transcription](TRANSCRIPTION.md); credential restrictions and spending controls are documented in [security operations](SECURITY_OPERATIONS.md#provider-controls-and-exposure).

Success is 200 JSON described by the named `TranscriptionCredential` schema, with only nonempty `value` and positive integer `expires_at` (Unix timestamp in seconds). Treat `value` as a bearer secret: never log/cache/persist it. Expiry is 60 seconds for creating connections, not a session-duration cap. The browser exchanges SDP and streams audio directly to OpenAI. No CORS access is granted. Responses are private/no-store. OPTIONS is 204 with `Allow: POST, OPTIONS`; unsupported methods are coded 405.

Origin failures return 403 `CROSS_ORIGIN_REQUEST`; missing/invalid/expired sessions return 403 `SESSION_REQUIRED`. Distributed quota limits return 429 `RATE_LIMITED` with required `Retry-After` (positive integer seconds). Disabled/missing feature configuration, invalid provider credentials and provider failures return 503 `TRANSCRIPTION_UNAVAILABLE`. Like other API failures these use `{ "error": { "code": "...", "message": "..." } }`; clients branch on code/status rather than display text. Unexpected authentication/server failures use the documented 500 `INTERNAL_ERROR`. No upstream details or credentials appear. See the generated OpenAPI operation for its schema. Issuance uses atomic per-owner DynamoDB counters and fails closed on backend failure. See [security operations](SECURITY_OPERATIONS.md) for policies, deployment and provider spending limitations.

## Draft paragraph and filler cleanup

`POST /api/shares/cleanup` uses the named `DraftText` schema for request and successful response. It accepts only `{ "text": "finalized draft" }` under the same 10,000-Unicode-code-point/64 KiB bounds as a save. It requires an exact same-origin Origin, an existing valid signed cookie and cleanup explicitly enabled; it neither creates a cookie nor writes a share. Successful 200 JSON is `{ "text": "cleaned draft" }`, with the same bounded nonblank schema and private/no-store caching. The response is a reviewable suggestion, not a saved record.

The server uses non-stored structured OpenAI Responses output to suggest paragraphs and remove clear fillers without summarizing. Invalid, incomplete, refused, blank or oversized results return coded 503 `CLEANUP_UNAVAILABLE`; the browser keeps the original. Validation retains the existing 400/413/415 codes. Origin failure is 403 `CROSS_ORIGIN_REQUEST`; missing/invalid/expired session is 403 `SESSION_REQUIRED`. Independent atomic per-owner cleanup quotas return 429 `RATE_LIMITED` with a positive `Retry-After` in seconds. Quota infrastructure failure returns 503 without a provider call. OPTIONS returns 204/Allow; unsupported methods return coded 405 with `Allow: POST, OPTIONS`.

Cleanup is automatically requested only after successful explicit Stop with new final words. No request is made for ordinary typing, provisional text, microphone cancellation or recording errors. Client edits/navigation cancel in-flight suggestions and prevent stale replacements. Successful cleanup replaces the editable draft; explicit Save is still required. The same server key needs Responses Request permission and model access. No provider request/response bodies or draft text are logged.

## Shared browser access boundary and client support

`server/http/middleware.ts` separates browser policy from identity: `sameOrigin` rejects a foreign supplied Origin on share creation but permits an absent one; `exactSameOrigin` requires a matching Origin on cleanup and transcription; `existingSession` verifies ownership without issuing or renewing a cookie. Paid operations compose exact Origin first, then existing-session authentication, then the applicable cleanup enablement, emergency controls and quota limits. Foreign requests cannot bootstrap or replace ownership. These checks do not authenticate native apps through an Origin header.

The named `ApiError` schema provides the shared envelope; response-specific schemas constrain the allowed codes. `DraftText` reuses the bounded share-input model; `TranscriptionCredential` is shared by server output validation and the browser parser. Both paid endpoints document required Origin headers and 429 Retry-After headers. Transcription OPTIONS is registered through the same OpenAPI method helper as cleanup. This changes the former transcription string-error response into the coded envelope; the website already handles credential failures by status. Any external consumer of the old string response must update.

See [API client boundaries](API_CLIENTS.md) for current browser support, native-client gaps and the HTTP/streaming split. Browser session preparation is implemented; native authentication, cross-origin access and versioned APIs remain separate decisions. Owner-scoped save idempotency is documented below.

### Transcription provider assertion

Session requests may include `X-STT-Provider` matching the immutable runtime bootstrap. A mismatch returns `503 TRANSCRIPTION_UNAVAILABLE` before contacting a provider. Missing headers remain compatible with legacy OpenAI clients. This header asserts configuration; it does not select a provider or replace existing origin/session checks.

Share creation and private reading enforce per-owner quotas and can return 429 with `Retry-After`; writes fail closed on quota backend failure (503), private reads fail open while preserving ownership. Public reading relies on edge protection and database resource controls, without application-wide counters. See [security operations](SECURITY_OPERATIONS.md).

Feature enable flags, migration behavior and provider configuration are maintained in [Transcription](TRANSCRIPTION.md#runtime-configuration). [Security operations](SECURITY_OPERATIONS.md) owns cookie lifetime, retention and operational quota policy.

## Retrying saves

`POST /api/shares` accepts an optional UUIDv4 `Idempotency-Key` header. Reuse it only for retries of the same normalized text, reading date and reading revision in the same signed owner session. A completed replay returns the original `201` representation and Location, preserving the ID, creation time, reading snapshot and public-link expiry, without a new creation-quota reservation or catalog lookup. A changed payload with the same key returns `409 IDEMPOTENCY_CONFLICT`; a malformed key returns `400 INVALID_IDEMPOTENCY_KEY`. Omitting the header retains independent-create behavior. Different owners have independent keys.

The browser retains the key only in the mounted draft's memory, including after an ambiguous timeout; it clears the key after confirmed success and selects a new key when the submitted content changes. Reloading loses the draft and key. There are no automatic save retries. The public share ID is always a separate server-generated UUID. Concurrent initial attempts can conservatively consume multiple quota reservations, but atomic storage creates at most one share for an owner/key.

## CSP report destination

`POST /api/csp-report` discards opaque browser reports with `204`, without parsing, logging, retaining data, setting a session cookie or calling storage/providers. Reports can contain private bearer URLs. It enforces a total five-second body-read deadline (`408 REQUEST_TIMEOUT`) and limits the actual body to 8 KiB even when Content-Length is inaccurate (`413` on overflow); a foreign supplied Origin returns `403`. `OPTIONS` returns `204` with `Allow: POST, OPTIONS`; other methods return `405`. The report-only policy uses this same-origin destination so WebKit activates it. Violations remain inspectable in browser developer tools; the endpoint provides no persistent telemetry.
