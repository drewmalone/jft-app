# Share API

This is the HTTP contract for the Next.js BFF in `jft-app`. It supports the current browser's private shares and UUID-link sharing. There are no login endpoints or client-selected owners. See [architecture](ARCHITECTURE.md) for implementation boundaries and [the README](../README.md#getting-started) for server setup.

## OpenAPI contract and libraries

`GET /api/openapi.json` serves OpenAPI 3.1, generated by `@hono/zod-openapi` from the route definitions and the Zod schemas used to validate requests. It is public schema metadata, contains no live shares/credentials, and does not issue a session cookie. HEAD returns its headers without a body; OPTIONS advertises GET, HEAD, OPTIONS.

Each operation owns its contract, selected middleware, and typed handler: [create](../src/shares/server/http/operations/create-share.ts), [list](../src/shares/server/http/operations/list-shares.ts), and [read](../src/shares/server/http/operations/read-share.ts). [Resource method handling](../src/shares/server/http/resource-methods.ts) owns HEAD documentation, OPTIONS, and 405 responses. [Shared OpenAPI helpers](../src/shares/server/http/openapi.ts) provide common schemas/headers and API metadata. [The server app](../src/shares/server/app.ts) registers these operations, configures shared failure handling, applies cache policy, and exposes the specification. Existing Next.js Route Handler files dispatch Web Requests to this app; there is no separate backend service. TypeScript definitions are the sole source of truth. Generated YAML is temporary and is not committed.

To generate and lint the contract locally:

```bash
npm run openapi:lint
```

This writes ignored `.tmp/openapi.yaml` and runs Spectral using [`.spectral.yaml`](../.spectral.yaml). `npm run openapi:generate` generates the file alone. Generation needs no running server, session secret, or network access. The standard `spectral:oas` rules apply; warnings and errors fail. `npm run check` includes this validation, and the GitHub Actions Verify job uploads the YAML as the `openapi` artifact, retained for seven days. There is no committed-YAML drift check.

Spectral checks contract conventions; it complements runtime validation and response tests.

`npm test` uses Swagger Parser to validate the serialized specification and Ajv's JSON Schema 2020-12 validator to check actual response bodies and required headers against it. Shared Zod validation remains authoritative for input transformations/refinements, including rejecting whitespace-only text after trimming. HTTP integration tests also exercise the real Next.js exports and framework boundary.

```bash
curl --silent --show-error --fail-with-body http://localhost:3000/api/openapi.json
```

No generated client or interactive documentation UI is required to consume the document.

## Session and response conventions

The server reads the `doorknob-session` cookie. If it is absent, malformed, expired, or incorrectly signed, a private create/list/detail endpoint creates a fresh random anonymous owner and issues a signed cookie with its response. The previous owner is never trusted or restored from invalid credentials; the new history is empty. This intentionally simple behavior is for the disposable in-memory prototype, with no recovery UI or endpoint. Cookie-based clients must retain and resend the cookie. Browser code uses same-origin credentials; nonbrowser clients need a cookie jar.

The cookie is HttpOnly, host-only, SameSite=Lax, and scoped to `/`. It has an absolute 30-day lifetime, with Secure added in production. Successful reads do not refresh its expiry. When the browser drops an expired cookie, its next request starts a new owner; an expired credential explicitly sent by a client also starts a new owner. Tabs sharing site cookies share an owner. Isolation requires separate cookie jars, such as a normal profile and a private profile; multiple private windows may share cookies with one another.

Signing prevents tampering; it does not encrypt the payload. The cookie contains the owner UUID and expiry and must be treated as a bearer credential. Do not log it, commit a cookie jar, or put it in an API body or URL. The `ownerId` field is omitted from share JSON; the UUID in the signed cookie is not a secret identifier on its own.

Responses carry `Cache-Control: private, no-store`. Share/error bodies use JSON; HEAD and OPTIONS have no body. Responses are returned directly as a share or an array; there is no `data` wrapper. Errors have this shape:

```json
{
  "error": {
    "code": "SHARE_NOT_FOUND",
    "message": "Share not found."
  }
}
```

Messages are intended for display. Branch on `error.code` and the HTTP status, never by matching message text. The fetch client exposes these as `ShareApiError.code`, `.status`, and `.message` and does not retry writes. Non-JSON HTTP failures retain their status with a safe fallback message.

## Save-time sharing URL

Create/list/detail responses include `shareUrl`, a relative URL such as `/s/{id}`. It is generated once when the record is constructed, before storage. Resolve it against the application origin for native sharing or copying. Reads return the original URL without renewal. There is no separate link-generation endpoint or extra sharing request. Treat URLs as bearer credentials and never log them.

The server rejects public reads seven days after the stored `createdAt` timestamp. The URL has no query parameters; adding or changing an `expires` query parameter has no effect. Expiration has no configuration, response metadata field, or UI label. Public responses exclude `shareUrl` and all owner metadata.

## Read a public share

`GET /api/public/shares/{id}` requires the cryptographically random UUIDv4, **no session**. The UUID itself is the bearer credential; every saved share can be read by someone who knows its ID during its lifetime. Existing cookies are ignored, including invalid ones; this endpoint never issues or replaces them. The server validates the UUID before storage lookup, then checks the stored creation time before returning content. No client-provided timestamp controls lifetime. Malformed UUIDs, expired shares and nonexistent records return **404/SHARE_NOT_FOUND**. Repository failures return generic 500. No signature or separate sharing secret is used.

Success is **200** with only `{ "reflection": { "id": "...", "date": "2025-04-23", "title": "...", "body": "..." }, "text": "A fictional thought." }`. It excludes owner ID, share creation metadata, kind and private history. Responses, including failures, carry `Cache-Control: private, no-store`, `X-Robots-Tag: noindex, nofollow` and `Referrer-Policy: no-referrer`. HEAD performs the same UUID and lifetime checks with no body. OPTIONS advertises `GET, HEAD, OPTIONS`; other methods return coded 405 with Allow. No CORS permission is granted.

The recipient HTML page is `/s/{id}` with the same UUID and service boundary. Valid links show the original reading date/title/body and written thoughts. Unavailable links show a generic message (HTML 200); unexpected server failures use a separate retryable error boundary with sanitized diagnostics and an initial HTTP 500 response; this is a minimal reading page, not private-history navigation. Pages have dynamic private/no-store caching and noindex/no-referrer headers and metadata. No session is established. No content-specific metadata or external tracking is added.

These are bearer links: recipients may forward, copy, or save content. There is no immediate revocation, token storage, link version counter, revoke endpoint, or delete endpoint. Future deletion of a share will invalidate its links by removing the record. Expiration does not remove records or recall received copies. A process restart loses all records. [Architecture](ARCHITECTURE.md#public-sharing-boundary) describes the trust boundary and tradeoffs.

## Create a share

`POST /api/shares`

Send `Content-Type: application/json` and a JSON object containing only `text`:

```json
{
  "text": "A fictional thought.\nOne small step."
}
```

The server accepts at most **10,000 Unicode code points in the raw text**, then trims surrounding whitespace and rejects an empty/whitespace-only result, nonstrings, missing text, and extra fields. Code points match JSON Schema's length semantics; combining sequences may contain several code points. The complete raw JSON body is limited to **64 KiB (65,536 bytes)**, including escaping and whitespace. Hono's body-limit middleware counts actual streamed bytes; a smaller claimed Content-Length cannot bypass this limit. A text-length violation returns 400/INVALID_SHARE; an oversized request returns 413/PAYLOAD_TOO_LARGE before JSON/schema validation. `ownerId`, `id`, `createdAt`, `kind`, and `reflection` are not accepted input fields. The session establishes ownership; the server supplies UUID, UTC ISO creation timestamp, `kind: 'text'`, and the current fixed reading snapshot. Snapshotting happens when the server saves, so changing the reading later does not alter existing records.

Success is **201 Created** with a share and a relative `Location: /api/shares/{id}` header. This identifies the private resource; the URL grants no access without the correct session. The following example uses fictional text and the current placeholder reading; the ID and timestamp are illustrative:

```json
{
  "id": "95eff0e1-bca7-4fd1-83d2-42ba330aab22",
  "createdAt": "2026-10-18T12:00:00.000Z",
  "kind": "text",
  "shareUrl": "/s/95eff0e1-bca7-4fd1-83d2-42ba330aab22",
  "text": "A fictional thought.\nOne small step.",
  "reflection": {
    "id": "acceptance-2025-04-23",
    "date": "2025-04-23",
    "title": "Acceptance is the answer to all my problems today.",
    "body": "Today, I can practice meeting life as it is. Acceptance gives me room to pause, let go of what I cannot change, and take one small step toward what I can."
  }
}
```

`reflection.date` is a calendar date, distinct from the creation timestamp. [Shared Zod schemas](../src/shares/model.ts) define the runtime field contract. The [server repository](../src/shares/server/storage/repository.ts) additionally stores `ownerId`; the handlers project records to the owner-visible schema before responding.

## List private shares

`GET /api/shares`

Success is **200 OK** with an array of this session's shares, newest creation timestamp first. No shares is `[]`, not an error. The Map implementation orders equal timestamps by newest insertion first. There are no query filters, pagination, or owner-selection parameters; ownership always comes from the verified cookie.

## Read one private share

`GET /api/shares/:id`

Success is **200 OK** with the same share shape as creation. This private endpoint requires the owner session. The same UUID also grants public read access through `/s/{id}` for seven days, so it must be treated as a credential. IDs with no corresponding record (including non-UUID strings) and IDs belonging to a different owner all return **404 Not Found** with the same error message. An invalid cookie starts a fresh owner, which cannot read a previous owner's share and therefore receives 404.

## Status and stable error codes

| Status | Code                   | Meaning                                                                               |
| ------ | ---------------------- | ------------------------------------------------------------------------------------- |
| 200    | —                      | List/detail succeeded; only a loaded empty array means empty history                  |
| 201    | —                      | Confirmed creation; clear the saved draft and show confirmation                       |
| 400    | INVALID_JSON           | The JSON body cannot be parsed                                                        |
| 400    | INVALID_SHARE          | Text is missing, blank, too long, or extra fields were supplied                       |
| 403    | CROSS_ORIGIN_REQUEST   | POST supplied a foreign Origin                                                        |
| 404    | SHARE_NOT_FOUND        | Detail record is absent or inaccessible to this owner                                 |
| 405    | METHOD_NOT_ALLOWED     | This resource does not implement that App Router HTTP method; includes Allow          |
| 413    | PAYLOAD_TOO_LARGE      | Raw request body exceeds 65,536 bytes                                                 |
| 415    | UNSUPPORTED_MEDIA_TYPE | POST content type is missing, invalid, or not application/json                        |
| 500    | INTERNAL_ERROR         | Configuration, repository, or other internal operation failed; details remain private |

On failed saves, retain the draft. Correct 400/413 input, use JSON for 415, and check the same-origin/proxy setup for 403. Private reads with invalid cookies start a fresh owner, not account recovery. 500 is generic: resolve the server/connection problem and consider the ambiguous-write caveat below before retrying.

500 can occur on private share operations; OPTIONS and the specification do not require a session. Media types are parsed with the `content-type` library: valid case-insensitive spellings such as `Application/JSON; Charset="UTF-8"` are accepted; syntactically invalid headers and other JSON subtypes are not accepted. A valid header is normalized before the OpenAPI JSON validator runs. POST also compares a supplied Origin to the browser-facing Host and request protocol. A missing Origin is allowed for nonbrowser clients. There is no cross-origin API/CORS support. Deploy behind HTTPS and a proxy that preserves or correctly supplies the original Host and protocol; do not rewrite these to an unrelated internal hostname.

A new session cookie can accompany a controlled POST validation error because the middleware establishes a session first. Foreign-origin rejections and internal 500 failures do not issue a cookie. [Session middleware](../src/shares/server/http/middleware.ts) and [HTTP errors](../src/shares/server/http/errors.ts) own this behavior. POST origin validation runs first: a foreign Origin receives 403 without reading, creating, or replacing a session, even if a supplied cookie is invalid. For accepted origins, verified or fresh anonymous ownership is established before media-type, size, JSON, and schema checks. Invalid cookies never supply ownership.

## HEAD, OPTIONS, and unsupported methods

| Resource          | Allow                    |
| ----------------- | ------------------------ |
| /api/shares       | GET, HEAD, POST, OPTIONS |
| /api/shares/{id}  | GET, HEAD, OPTIONS       |
| /api/openapi.json | GET, HEAD, OPTIONS       |

Hono implements HEAD by running the GET checks and removing the body. A private detail can therefore return 200 or 404 with an empty body and the corresponding GET headers (or generic 500 on server failure). Initial HEAD requests may issue a cookie, just like GET.

OPTIONS returns 204, no body, and the Allow header. It does not read/create sessions, even if a supplied cookie is invalid, and it grants no CORS permission. App Router methods not implemented by a resource (PUT/PATCH/DELETE, plus POST on a detail/spec resource) return the coded 405 envelope, private/no-store, and Allow without issuing a cookie. Methods Next.js rejects before dispatch, malformed transport requests, and framework redirects remain outside the custom JSON envelope.

## Try it locally

Start `npm run dev` in one terminal. In another terminal, run the following with fictional text only. This uses the existing Node.js runtime to extract the generated ID; no additional API tool is required beyond curl.

```bash
doorknob_base_url=http://localhost:3000
doorknob_cookie_jar="$(mktemp)"

doorknob_created_share="$(curl --silent --show-error --fail-with-body \
  --cookie "$doorknob_cookie_jar" --cookie-jar "$doorknob_cookie_jar" \
  --header 'Content-Type: application/json' \
  --data '{"text":"A fictional thought. One small step."}' \
  "$doorknob_base_url/api/shares")"
printf '%s\n' "$doorknob_created_share"

doorknob_share_id="$(printf '%s' "$doorknob_created_share" | \
  node -e 'let body = ""; for await (const chunk of process.stdin) body += chunk; console.log(JSON.parse(body).id)')"

curl --silent --show-error --fail-with-body \
  --cookie "$doorknob_cookie_jar" "$doorknob_base_url/api/shares"
curl --silent --show-error --fail-with-body \
  --cookie "$doorknob_cookie_jar" "$doorknob_base_url/api/shares/$doorknob_share_id"

# A separate client without this cookie cannot access the first owner's share: 404.
curl --silent --show-error --output /dev/null --write-out '%{http_code}\n' \
  "$doorknob_base_url/api/shares/$doorknob_share_id"

# Delete the temporary bearer credential when finished.
rm -- "$doorknob_cookie_jar"
```

The first POST issues the cookie; subsequent requests use it. On a browserless HTTP production-mode run, curl will not send a Secure cookie over arbitrary plain HTTP hosts. Use the development server for this example, or HTTPS for a hosted server.

## Retention and failed-write semantics

Records survive requests only in the same Node process. Restarting that process clears them. Replicas/serverless instances do not share the Map; this is not durable deployment storage. Cookie removal, cookie expiry, and signing-key changes lose access but do not delete records from the running Map. There is no delete endpoint or automatic record expiry; the Map retains records until the process exits. See [data lifecycle](DATA_GLOSSARY.md#app-data-lifecycle).

There are no idempotency keys or automatic retries. If the server commits but its response is lost, a client sees a failed request despite a stored share. Check history before retrying an ambiguous write if duplicate text matters. UI duplicate prevention blocks repeated submissions only while a save is pending. Do not describe a rejected fetch as proof that no write occurred.

## Live transcription credentials

`POST /api/transcription/session` issues an ephemeral OpenAI credential; it does not save text or accept audio. It requires an exact same-origin `Origin` header, an existing valid signed anonymous-session cookie, and server configuration `STT_ENABLED=true`. An invalid/missing session is rejected rather than replaced. No request fields configure the provider. The server fixes initial transcription-only settings, model `gpt-live-transcribe`, English, near-field noise reduction, and client-side turn commits.

Success is 200 JSON described by the named `TranscriptionCredential` schema, with only nonempty `value` and positive integer `expires_at` (Unix timestamp in seconds). Treat `value` as a bearer secret: never log/cache/persist it. Expiry is 60 seconds for creating connections, not a session-duration cap. The browser exchanges SDP and streams audio directly to OpenAI. No CORS access is granted. Responses are private/no-store. OPTIONS is 204 with `Allow: POST, OPTIONS`; unsupported methods are coded 405.

Origin failures return 403 `CROSS_ORIGIN_REQUEST`; missing/invalid/expired sessions return 403 `SESSION_REQUIRED`. Process-local rate limits return 429 `RATE_LIMITED` with required `Retry-After: 60` (seconds). Disabled/missing configuration, invalid provider credentials and provider failures return 503 `TRANSCRIPTION_UNAVAILABLE`. Like other API failures these use `{ "error": { "code": "...", "message": "..." } }`; clients branch on code/status rather than display text. Unexpected authentication/server failures use the documented 500 `INTERNAL_ERROR`. No upstream details or credentials appear. See the generated OpenAPI operation for its schema. The issuance guard is five attempts per owner/minute per process, with bounded memory. It is not distributed authorization or a hard spending cap. Protect the hosted preview and follow [deployment instructions](TRANSCRIPTION.md). The anonymous session and share-save endpoints remain unchanged.

## Draft paragraph and filler cleanup

`POST /api/shares/cleanup` uses the named `DraftText` schema for request and successful response. It accepts only `{ "text": "finalized draft" }` under the same 10,000-Unicode-code-point/64 KiB bounds as a save. It requires an exact same-origin Origin, an existing valid signed cookie and `STT_ENABLED=true`; it neither creates a cookie nor writes a share. Successful 200 JSON is `{ "text": "cleaned draft" }`, with the same bounded nonblank schema and private/no-store caching. The response is a reviewable suggestion, not a saved record.

The server uses non-stored structured OpenAI Responses output to suggest paragraphs and remove clear fillers without summarizing. Invalid, incomplete, refused, blank or oversized results return coded 503 `CLEANUP_UNAVAILABLE`; the browser keeps the original. Validation retains the existing 400/413/415 codes. Origin failure is 403 `CROSS_ORIGIN_REQUEST`; missing/invalid/expired session is 403 `SESSION_REQUIRED`. A separate process-local five-attempts/minute limit returns 429 `RATE_LIMITED` with `Retry-After: 60`. These are burst guards, not distributed authorization or hard spending limits. OPTIONS returns 204/Allow; unsupported methods return coded 405 with `Allow: POST, OPTIONS`.

Cleanup is automatically requested only after successful explicit Stop with new final words. No request is made for ordinary typing, provisional text, microphone cancellation or recording errors. Client edits/navigation cancel in-flight suggestions and prevent stale replacements. Successful cleanup replaces the editable draft; explicit Save is still required. The same server key needs Responses Request permission and model access. No provider request/response bodies or draft text are logged.

## Shared browser access boundary and client support

`http/middleware.ts` separates browser policy from identity: `sameOrigin` rejects a foreign supplied Origin on share creation but permits an absent one; `exactSameOrigin` requires a matching Origin on cleanup and transcription; `existingSession` verifies ownership without issuing or renewing a cookie. Paid operations compose exact Origin first, then existing-session authentication, then operation enablement/limits. Foreign requests cannot bootstrap or replace ownership. These checks do not authenticate native apps through an Origin header.

The named `ApiError` schema provides the shared envelope; response-specific schemas constrain the allowed codes. `DraftText` reuses the bounded share-input model; `TranscriptionCredential` is shared by server output validation and the browser parser. Both paid endpoints document required Origin headers and 429 Retry-After headers. Transcription OPTIONS is registered through the same OpenAPI method helper as cleanup. This changes the former transcription string-error response into the coded envelope; the website already handles credential failures by status. Any external consumer of the old string response must update.

See [API client boundaries](API_CLIENTS.md) for current browser support, native-client gaps and the HTTP/streaming split. This change adds no native authentication, session-bootstrap endpoint, cross-origin permission, versioned API, idempotency key or persistent storage.
